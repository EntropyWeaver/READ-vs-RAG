# Benchmark schema and annotation protocol

One JSON object per line in `questions.jsonl`. Lines starting `//` are comments.

## Fields

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | Unique, stable. Prefix by category (`arith-001`). Never renumber a released id. |
| `category` | string | yes | `lookup` \| `aggregation` \| `arithmetic` \| `navigation` \| `unanswerable` \| `conversion_limited` |
| `difficulty` | string | no | `easy` \| `medium` \| `hard` — annotator's judgement, reported but not scored |
| `question` | string | yes | Asked verbatim. No hints about where to look. |
| `target_statement` | string | no | Annotator's note on where the answer lives. **Never shown to any system.** |
| `reference_answer` | string | yes* | The gold answer in prose. Given to the LLM judge. |
| `expected_figures` | list[float] | yes* | Gold figures the **answer** must state, normalized to crore. |
| `operand_figures` | list[float] | arithmetic only | The figures the answer is **computed from**. `--verify` checks these appear near `gold_lines`. |
| `gold_lines` | list[int] | yes* | 1-indexed lines that contain the evidence. Used for coverage and by `--verify`. |
| `gold_pages` | list[int] | derived | Computed from `gold_lines`; don't set by hand. |
| `unanswerable` | bool | yes | If true, the correct behaviour is to decline. |
| `verified` | bool | yes | **A human read the figures off the document.** |
| `notes` | string | no | Why the question is interesting; annotator context. |

\* Required unless `unanswerable` is true.

## The verification rule

**A row with `verified: false` produces a meaningless score.** The runner accepts
unverified rows so the plumbing can be smoke-tested, but no number from them
belongs in the paper.

Gold figures are read off the document by a person. They are not generated by a
model, not copied from another source, and not inferred from a related figure.
`02_annotate_benchmark.py --verify` re-checks that every verified row's figures
still appear near its gold lines, which catches silent drift if the PDF is
re-converted.

## Annotating

```bash
uv run python scripts/02_annotate_benchmark.py --status     # what's left
uv run python scripts/02_annotate_benchmark.py --annotate   # work through it
uv run python scripts/02_annotate_benchmark.py --verify     # re-check
```

Inside `--annotate`: `/s <query>` searches, `/r <start> <end>` reads a span,
`/skip` moves on, `/quit` saves and exits. Each answered row is written
immediately, so an interrupted session loses nothing.

## Conventions

**Units.** Store every figure in **crore**. The annotator script converts lakh
and thousand automatically. If a statement prints in a different unit, convert
when recording and say so in `notes`.

**Signs.** The book writes negatives as `(-)1,234` or `(1,234)`. Record the
signed value: `-1234.0`.

**Rounding.** Record the figure exactly as printed. The grader applies 0.5%
relative tolerance, so `48964.89` and `48964.9` match while `48964` and `18942`
do not.

**Multi-part answers.** List every figure the answer must contain in
`expected_figures`; grading requires all of them.

**Derived answers.** For arithmetic questions, record the *derived* figure in
`expected_figures`, the inputs in `operand_figures`, and the operand lines in
`gold_lines`. Put the derivation in `reference_answer` so the judge sees the
working.

`--verify` treats arithmetic rows differently on purpose: it checks that the
**operands** appear near the gold lines, and that the **derived answer does
not appear anywhere in the corpus**. A derived value that is printed in the
document means the question is a lookup wearing a calculation's clothes, and
the check fails.

**Conversion-limited questions.** A separate category for questions whose
answer is present in the *PDF* but destroyed by the *conversion*. The exemplar
is `conv-001`: Statement No. 18 prints interest rates of 11.00 and 10.00, but
the converter puts the digits in one table cell and the decimal point in the
cell below, so the Markdown reads `1100` and `1000`.

These invert the usual validation: `--verify` asserts the correct figure is
**absent** from the corpus, and fails the row if it turns out to be present
(which would mean it is not conversion-limited after all).

They exist to separate two failures that look identical in an accuracy score:
retrieval failing to find the evidence, and retrieval succeeding on evidence
that the conversion already destroyed. The second is a ceiling shared by every
retrieval method, so it belongs in its own bucket rather than being charged to
whichever system happened to be under test.

**False-premise questions.** A question can name the wrong statement while the
figures exist elsewhere. These are worth keeping deliberately: they detect
whether a system accepts the premise and fabricates a citation to match, which
accuracy alone scores as correct. `arith-001-fp` is the worked example — a
correct answer must give the figures *and* reject the stated location.

## Target composition

Roughly 120–200 questions gives usable resolving power (see
`stats.min_detectable_delta`). A sensible split:

| Category | Share | Why |
|---|---|---|
| `lookup` | ~30% | The base case: one figure, one cell |
| `aggregation` | ~20% | Spans more text than any top-*k* slice |
| `arithmetic` | ~25% | Exactness-critical; the paper's core claim |
| `navigation` | ~10% | Exercises structure, not just text |
| `unanswerable` | ~15% | Without these, hallucination is unmeasured |

Keep unanswerable probes plausible — a future year, a different state, a volume
that exists but isn't this document. A probe that is obviously absurd measures
nothing.
